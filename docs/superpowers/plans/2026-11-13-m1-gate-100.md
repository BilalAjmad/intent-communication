## Review Focus

The five input classes most likely to bite a real user, which no current test exercises. Each gets a test in the phase that owns the code.

1. **A stale lock file left by a process killed with `SIGKILL` mid-write.** The scene lock reclaims on pid-liveness; the *object* lock has no staleness rule at all — a crashed process leaves `<objectId>.lock` on disk forever and every later write to that object returns `E_LOCKED` permanently. → Phase 2.
2. **Two agents writing the same object concurrently** must not silently lose an update, and the second must get `E_CONFLICT` (not `E_LOCKED`, which the current core test wrongly asserts). → Phase 2.
3. **A scene ID containing `..` or a path separator** must never escape `.intent/scenes/`. `createFileStoragePort` has traversal protection; `core`'s `createStoragePort` does not — the two storage ports disagree. → Phase 1.
4. **An extremely long object ID** (e.g. 4000 chars) becomes a filesystem path segment on Windows and can exceed `MAX_PATH`, throwing `ENOENT` instead of a clean `E_BAD_REQUEST`. → Phase 1.
5. **A patch whose `path` traverses to a sibling object** (e.g. `../../otherObject/props/content`) must be rejected, not applied. The M3 mutation test claims to cover "patch path traverses to target object" but does not assert the *rejection* of an escaping path. → Phase 2.

- [ ] **Step 3: Make `isProcessAlive` cheap and Windows-native**

`packages/core/src/ports.ts:272-293` spawns PowerShell (`Get-Process -Id`) on every check. PowerShell startup costs 300–1000ms, and `acquireSceneLock` calls it on *every* one of its 12 attempts, so a contended scene lock takes **6+ seconds** to fail while holding the scene lock — this is the actual cause of the "1 in 6" E_LOCKED flake.

Replace the PowerShell path with Node's own check, which works on win32:

```ts
async function isProcessAlive(pid: number): Promise<boolean> {
  try {
    process.kill(pid, 0);
    return true;
  } catch (err) {
    return (err as NodeJS.ErrnoException).code === "EPERM";
  }
}
```

`EPERM` means the process exists but is owned by another user — treat it as alive.

- [ ] **Step 4: Verify the scene-lock timing**

Run: `pnpm --filter @intent/core exec vitest run src/multi-process.test.ts`
Expected: PASS, and the "4 procs on different objects" test completes in well under 5 seconds (currently ~28s when it fails).

- [ ] **Step 5: Make object locks reclaimable (Review Focus #1)**

`acquire` (`ports.ts:307-329`) writes a bare owner token and never expires. Change it to write JSON `{ pid, ownerToken, createdAt }` via `flag: "wx"`. On `EEXIST`, read the file: if `createdAt` is older than 10s **or** the owner pid is not alive, unlink and retry (same reclaim rule the scene lock already uses). Keep the 50-attempt / 5ms backoff for the genuinely-contended case.

`release` must only unlink a lock file this owner holds — compare the `ownerToken` before unlinking, so a stale reclaim followed by a late release cannot delete a *new* owner's lock.
